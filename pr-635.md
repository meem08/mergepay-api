## Summary

Enforces strict, database-backed membership and role verification on every group management route in `src/routes/groups.ts`, using reusable Fastify `preHandler` hooks. Non-members are refused with `403 FORBIDDEN` before any handler, body parse, or write runs, non-admins cannot reach administrative routes, and state changes against an **archived** group are now refused as well.

Closes #635

## What the hooks do

`src/middleware/group-guard.ts` exposes the reusable guards:

```ts
requireGroupMember({ param: "id" })        // member or admin of the group
requireGroupMember({ param: "id", active: true })  // …and the group is not archived
requireGroupAdmin({ param: "id" })         // admin only
requireGroupAdmin({ param: "id", active: true })   // …and the group is not archived
```

Both are thin, typed wrappers over `requireGroupRole` in `src/plugins/group-access.ts`, which:

- reads the group id **only** from the named path parameter (never from the body, query string, or headers);
- reads the caller's role **only** from the `GroupMember` row in the database — a claimed `role` in the payload, query, or `x-role` header is ignored, and any stored role other than exactly `admin` fails an admin check;
- resolves the owning group from the expense row for `/expenses/:id` routes (`fromExpense: true`);
- attaches the verified membership to `req.groupMembership` (read it with `groupMembership(req)`), so handlers never re-derive authorization from request data;
- returns `401` before any lookup when unauthenticated, `400 VALIDATION_ERROR` for a malformed id, `404 NOT_FOUND` for an unknown group, and `403 FORBIDDEN` for a non-member or an insufficient role;
- keeps each guard **last** in the route's `preHandler` chain, so user-keyed rate limits run first and a non-member probing group ids still spends their budget.

Mutating handlers keep re-running `requireAdmin` inside their Prisma transaction. The guard is the fast rejection; the transactional re-check closes the race where a concurrent demotion or removal lands between the guard and the write.

## Route coverage in `src/routes/groups.ts`

| Route | Guard |
| --- | --- |
| `GET /groups/:id` | member (archived group stays readable) |
| `GET /groups/:id/balance` | member (archived group stays readable) |
| `PATCH /groups/:id` | **admin of a live group** |
| `POST /groups/:id/invite` | **admin of a live group** |
| `PATCH /groups/:id/members/:memberId` | **admin of a live group** |
| `DELETE /groups/:id/members/:memberId` | **admin of a live group** |
| `POST /groups/:id/members/role` | **admin of a live group** |
| `POST /groups/:id/leave` | member (always allowed, including on an archived group) |
| `POST /groups/:id/archive` | admin (no `active` check — archiving is the transition that creates the closed state, and it is idempotent) |

The `active` requirement is the new strictness: these five mutations previously accepted an admin of an archived group, which let a closed group be renamed, re-populated, and have its membership rewritten. That contradicts the documented contract of `requireGroupRole` (archival closes a group to new state, while history stays readable — #648) that `expenses.ts` and `settlements.ts` already follow for their writes.

**On "deleting groups":** the API intentionally has no hard-delete endpoint for a group. Archival (`POST /groups/:id/archive`) is the lifecycle end, and it retains the ledger, settlements, and audit trail that a cascade delete would destroy. It is admin-guarded as shown above; no destructive route was added here.

## Tests

New `tests/group-management-authorization.test.ts` (45 tests), stubbing only the Prisma boundary:

1. **Hooks in isolation** — non-member `403` with the handler never invoked; member admitted with `req.groupMembership` populated; admin passes both hooks; regular member `403` on admin hooks; `active` hooks `403 "Group is archived"` while read hooks still admit members; non-member of an archived group still refused; `401` unauthenticated and `400` malformed id with **no** membership lookup; role claimed in body/query/headers ignored; authorization always performed against the path group id.
2. **The real app, every group management route** — parameterized over the route table:
   - non-member → `403 FORBIDDEN`, zero writes (`group.update`, `groupMember.update/delete`, `invite.create`, `invitation.create`, `auditLog.create`, `$transaction` all untouched);
   - regular member → `403` on every admin-only route, zero writes;
   - admin of an archived group → `403 "Group is archived"` on every mutation, zero writes;
   - archived group stays `200` for reads, `leave`, and `archive`;
   - admin of a live group is admitted by the guard;
   - unknown group → `404` without leaking existence;
   - unauthenticated → `401` before any membership lookup.
