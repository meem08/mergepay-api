## Summary

Adds a single, strict validation layer for every on-chain group expense settlement payload, and validates the resulting Stellar payment intent — public keys, asset, amount, memo, and signing window — before an unsigned envelope can be built.

Previously the settlement routes each declared their own inline Zod schemas: they were non-strict (unknown keys were silently stripped, so a client that sent an absolute deadline or a misspelled amount got a success for something the server ignored), `toUserId` was an unbounded `z.string()`, `signedXdr` was only `z.string().min(1)` with no size or whitespace rules, and nothing checked the source/destination public keys before they were handed to `TransactionBuilder`.

Closes #644

## New module: `src/validations/settlement.ts`

| Schema | Enforces |
| --- | --- |
| `settlementPublicKeySchema` | ed25519 `G…` key via the SDK's `StrKey.isValidEd25519PublicKey`; rejects secret seeds, muxed addresses, bad checksums, truncated keys |
| `settlementIdentifierSchema` | user/settlement ids: trimmed, 1–64 chars, `[A-Za-z0-9_-]` only |
| `settlementShareSchema` | a participant's share: valid participant id + stroop-exact positive amount |
| `settleExpensePayloadSchema` | `POST /expenses/:id/settle` body: optional asset override (supported asset, issuer only with a code) + bounded signing window; strict |
| `freeformSettlementPayloadSchema` | `POST /groups/:id/settlements` body: recipient id, amount, asset, signing window; strict |
| `signedXdrSchema` | envelope: trimmed, non-empty, ≤ 100 000 chars, no internal whitespace |
| `settlementConfirmPayloadSchema` / `settlementExecutePayloadSchema` | confirm and execute bodies, including a character-restricted `settlementId`; strict |
| `settlementIntentSchema` | the complete payment intent: both public keys, supported asset on the configured network, representable positive amount, memo code, bounded validity window; strict |

Asset rules and amount rules are not re-implemented: they delegate to the existing single source of truth (`src/lib/money.ts` via `refineStellarAsset` / `stellarAmountSchema`), so request validation and XDR construction cannot drift. Sanitization is deliberately narrow — envelope whitespace is trimmed, amounts keep the shared whitespace-padding rejection, nothing else is rewritten. No schema accepts, returns, or stores a private key.

## Integration into the pipeline (`src/routes/settlements.ts`)

- `POST /expenses/:id/settle` parses with `settleExpensePayloadSchema`, then validates the **participant share** being settled (`settlementShareSchema` over the persisted `shareAmount`) and uses that validated amount for the XDR.
- `POST /groups/:id/settlements` parses with `freeformSettlementPayloadSchema` before any recipient lookup, limit check, write, or Horizon call.
- `POST /settlements/:id/confirm` and `POST /settlements/execute` parse their bodies with the shared schemas — ahead of the settlement lookup and the Idempotency-Key requirement — so a malformed envelope is never persisted or cached as an idempotent result.
- `buildSettlementXdr()` parses the full intent with `settlementIntentSchema` **before** the Horizon account load. A malformed source or destination key, an unsupported asset, an unrepresentable amount, or an out-of-range window now fails with `400 VALIDATION_ERROR` instead of reaching `TransactionBuilder` or Horizon.
- The OpenAPI body annotations for confirm/execute now reference the same schemas the handlers enforce, so documentation and enforcement are one object.
- Removed the two long-unused `validateAsset` / `validateAmount` imports that the old inline schemas had left behind.

## Behaviour changes (both deliberate, both stricter)

1. **Unknown body keys are now a `400`** rather than silently stripped. This follows the precedent already documented in `src/schemas/groups.ts`: a client that sends a field the server does not honour must not receive a success that implies it did. Concretely, a client-supplied `expiresAt` on a settle-up is now rejected instead of ignored (see the updated expectation in `tests/intent-expiration-routes.test.ts`).
2. **A malformed stored public key fails before the XDR** — `400 VALIDATION_ERROR` with the SDK's message, no Horizon call, no envelope. Two test fixtures that used placeholder keys (`GPAYERAAAA…`, `GSHAREAAAA…`) were updated to real generated keypairs, since those strings were never valid Stellar addresses.

## Tests

- `tests/validations/settlement.test.ts` — 40 schema unit tests: valid and invalid public keys (including secret seeds and bad checksums), every request body, strict unknown-key rejection, amount precision/range/whitespace/exponent cases, asset support and issuer mismatch, the native-asset-with-issuer contradiction, envelope size/whitespace, and the full intent (including the default validity window).
- `tests/settlement-payload-validation.test.ts` — 20 route-level tests proving the wiring: a valid settle-up reaches `loadAccount`/`buildPayment` with the validated fields; twelve invalid payloads each return `400 VALIDATION_ERROR` with **no** Stellar work and no settlement row; a malformed recipient or payer key is refused before the envelope is built; a persisted share with 8 decimal places is refused; confirm/execute bodies are rejected before the settlement lookup.
- Existing suites updated only where behaviour deliberately changed (see above).
